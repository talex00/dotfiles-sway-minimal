# Работа с Sway Minimal

## Назначение и рабочая папка

Это исходники минималистичного рабочего окружения на Sway, разворачиваемого
через GNU Stow. Помогай исправлять ошибки, создавать темы и развивать установщик,
сохраняя лёгкость окружения и существующую архитектуру.

Запускай агента из корня этого репозитория, а не из `~/.config`.
Не добавляй AI-сервисы в автозапуск рабочего стола: агент — инструмент разработки.
Общайся с пользователем на русском.

## Карта проекта

- `sway/.config/sway/config` — основной конфиг Sway.
- `sway/.config/sway/scripts/` — меню и скрипты окружения;
  `helpers/` — служебные компоненты.
- `sway/.config/sway/themes/<имя>/` — исходники тем для приложений.
- `sway/.config/waybar/` — панель и независимо выбираемые стили.
- `sway/.local/bin/` — обёртки запуска и вспомогательные программы.
- `foot/`, `fuzzel/`, `swaync/`, `fish/`, `thunar/`, `xfce/`,
  `xsettingsd/` — остальные Stow-пакеты.
- `install.sh`, `scripts/install/`, `uninstall.sh` — установка и удаление.
- `tests/check.sh` — базовые проверки; `experimental/test-*` —
  дополнительные проверки движка, миграции и установки.

Несмотря на название, `experimental/` содержит действующий Theme Engine 2.0.
Путь выполнения: `sway/.config/sway/scripts/look.sh` →
`sway/.config/sway/scripts/helpers/look-v2.sh` → `experimental/look-v2.sh`.
Перед изменением этого механизма прочитай `experimental/INTEGRATION.md`
и соответствующий код.

`README.md` — обзор и пользовательские инструкции, но отдельные разделы
могут описывать старую механику. `AUDIT-2026-11.md` — исторический снимок,
не список заведомо актуальных ошибок. Проверяй утверждения по текущему коду;
не принимай записанное в документации состояние конкретной машины за текущее.

## Порядок работы

1. Проверь `git status --short`; отличай существующие правки от своих.
2. Прочитай относящийся к задаче код и проверки. Не загружай весь проект
   и всю историю документации без необходимости.
3. Выбирай минимальное достаточное изменение. Не делай попутных рефакторингов,
   новых слоёв абстракции, зависимостей или документационных деревьев.
4. Для исправления ошибки по возможности добавь регрессионную проверку.
5. Выполни подходящие проверки и кратко сообщи результат, ограничения
   и необходимость отдельного применения в живой сессии.

Сохраняй совместимость с целевыми дистрибутивами: Ubuntu 24.04, Debian,
Fedora и Arch. Не предполагай, что возможности свежих пакетов доступны
в Ubuntu 24.04. Сохраняй существующий диалект shell и проверяй shebang.
Тема, стиль панели и пользовательские параметры должны оставаться независимыми.

## Безопасность живого окружения

- Разработка идёт в действующем пользовательском окружении, не в одноразовой
  VM. Тесты не должны требовать перезагрузки, выхода из сессии, её reload,
  установки пакетов или остановки пользовательских процессов.
- Репозиторий может быть связан с живым HOME через Stow-симлинки.
  Правка исходника тоже может повлиять на рабочую сессию; проверяй связи
  перед потенциально опасными изменениями.
- Различай исходники, локальные настройки и сгенерированные файлы.
  Исправляй источник проблемы, а не только результат генерации.
- MIME-ассоциации и личные `.desktop`-ярлыки хранятся в HOME, не в Stow-пакетах.
  Не связывай изменяемые приложениями файлы с отслеживаемыми исходниками.
- Не перезаписывай чужие изменения, не выполняй reset/clean и не создавай
  коммиты без запроса пользователя.
- Без явного согласия не устанавливай пакеты, не выполняй установку,
  удаление, миграцию, Stow в настоящий HOME, применение темы, reload
  или перезапуск процессов живой сессии. Не запускай удалённый установщик:
  его bootstrap может сбросить локальный репозиторий.
- Не изменяй машинные настройки мониторов, рабочих пространств, обоев,
  GTK/dconf и пользовательские предпочтения ради теста.
- Для проверок используй временный HOME и изолированные XDG-каталоги.
  Одного подменённого HOME недостаточно для изоляции Sway IPC и D-Bus:
  перед запуском теста прочитай, какие внешние действия он выполняет.
- Не запускай глобальный `stow -R`. Для разрешённого развёртывания используй
  существующий механизм проекта и учитывай `--no-folding`.

## Проверки

`install.sh` — ядро проекта: через него пользователь устанавливает и обновляет
дотфайлы. Перед каждым коммитом обязательно проверяй его и `scripts/install/`:
синтаксис и локальные режимы `--help`, `--check`, `--dry-run` во временном
HOME с изолированными XDG-каталогами. Эти проверки включены в `tests/check.sh`.
Не запускай для проверки `--install` или удалённый bootstrap.

Базовая команда из корня: `sh tests/check.sh`.
Она проверяет shell-синтаксис и, если доступен Stow, его работу во временном
HOME. ShellCheck и shfmt необязательны; их замечания сейчас не делают
проверку неуспешной. Это не полная проверка установщика и графической сессии.

Дополнительные тесты выбирай по задаче, предварительно прочитав их.
Не считай отсутствие инструмента успешной проверкой. В результате явно
различай выполненные проверки, пропуски и то, что требует визуального
подтверждения. Не заявляй о поддержке дистрибутива без соответствующей проверки.

## Накопление навыков

Не создавай skills заранее или автоматически после каждой задачи.
Сначала добейся результата, который устраивает пользователя.
Когда пользователь попросит сохранить опыт, создай проектный skill
в `.opencode/skills/<имя>/SKILL.md` на основе реально выполненной работы:
когда применять, какие шаги сработали, как проверять и каких ошибок избегать.
Не фиксируй временные пути, секреты и случайные особенности одной машины.
Если подходящий skill уже есть, предпочитай уточнить его, а не создавать дубликат.

Держи этот файл кратким: здесь постоянные правила и навигация,
а не журнал сессий и не каталог гипотетических процедур.
